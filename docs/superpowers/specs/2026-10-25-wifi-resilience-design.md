# Устойчивый Wi-Fi: live view без обрывов при слабом сигнале

Дата: 2026-10-25. Статус: сделано на Mac и Android (ветка `feat/wifi-resilience`). Пользователь поручил решать самому: «при плохом
сигнале можно портить немного качество, но при хорошем — чтобы не портило».

Основа — исследование `reports/Устойчивый стриминг при слабом WiFi.md` и опыты на камере ниже.

## Что измерено на камере (ZV-E10, прошивка 2.00, Wi-Fi через роутер)

- **0xD26A LiveViewImageQuality по Wi-Fi работает** (запись 0x9205, UINT8): 2 — высокое, 1024×576, ~72 КБ на кадр;
  1 — низкое, 640×360, ~34 КБ. Размер кадра почти постоянный. Высокое при 25 к/с — ~1,8 МБ/с (~14 Мбит/с): на хорошем
  канале это почти потолок 2,4 ГГц камеры, на слабом — не помещается.
- Камера отвечает на ProbeRequest (13) программы на событийном канале за 5–50 мс.
- Камера отвечает на ICMP ping (3–13 мс). На macOS ping без root — `SOCK_DGRAM` + `IPPROTO_ICMP`;
  на Android — `InetAddress.isReachable`.
- **Зависшая сессия.** Пока старое соединение живо на уровне TCP, новое камера не принимает ~10 с (EOF после Init или
  молчит на OpenSession), потом сама отпускает старое. RST по старому соединению освобождает камеру сразу: новый полный
  сеанс через ~1,5 с. Блокировка на ~2,5 мин бывает, когда камера застряла на неподтверждённой передаче, а до неё не
  дошли ни наш FIN, ни RST — то есть когда программа закрыла соединение, пока связи не было.
- Голый Init без продолжения (Ack и сразу закрыть) камера переживает плохо: следующие Init какое-то время обрываются.

## Принципы

1. **Пауза — не обрыв.** Сеанс не закрываем, пока связь просто пропала: TCP сам доставит данные, когда она вернётся.
   Закрываем только при жёсткой ошибке (RST/EOF), когда связь вернулась, а TCP молчит, когда связи нет дольше 3 минут
   или когда камера отвечает на пробы, а на PTP молчит.
2. **Переподключение — сразу и тихо.** Старые сокеты — RST (камера освобождается сразу), новая попытка — немедленно,
   по тому же адресу, без поиска SSDP; дальше паузы 0,5 → 1 → 2 → 3 → 5 с.
3. **Картинка не пропадает.** Последний кадр остаётся на экране, поверх — состояние связи и сколько она длится.
   Настройки, таймер записи и лента снимков сохраняются; кнопки неактивны, пока сеанс не готов.
4. **Качество — по каналу.** По Wi-Fi высокое качество превью, пока канал его тянет; когда не тянет — низкое
   (640×360), с гистерезисом. По USB качество не трогаем. Настройка «Снижать качество превью при слабом Wi-Fi»
   (включена по умолчанию).

## Слежение за связью (транспорт PTP/IP)

Раз в 250 мс:

- `тишина` — сколько ничего не приходило ни по одному из двух соединений (считаются байты, а не целые пакеты).
- **Пульс.** Если нет неотвеченной пробы и с прошлой прошло ≥ 2 с — ProbeRequest по событийному каналу. Ответ даёт RTT
  и сам по себе — входящие байты, так что тишина честная и тогда, когда live view на паузе.
- **Провал связи** — ждём ответа (операция или проба, на которые камера раньше отвечала), а ничего нет ≥ 2,5 с. Пока он длится: ICMP ping камеры раз в секунду (тайм-аут 0,8 с), тайм-ауты
  транзакций не тикают (транзакции просто ждут).
- **Связь вернулась, а TCP молчит.** Ping ответил, а за 3 с после этого байтов так и нет — RST обоих соединений,
  транспорт закрыт с причиной «сброшено после провала» → переподключение.
- **Провал дольше 180 с** — закрыть, причина «связи нет».
- **Камера не отвечает.** Пробы отвечают, а транзакция ждёт ≥ 15 с без единого байта — закрыть обычным образом (связь
  есть, FIN дойдёт), причина «камера не отвечает».
- **Жёсткая ошибка** (RST/EOF/ошибка отправки) по любому соединению — закрыть, причина «оборвалось».
- Тайм-аут транзакции для вызывающего — 8 с без единого байта (большой файл идёт долго, но непрерывно). Сам по себе он
  сеанс не закрывает — это решает слежение.

Параметры сокетов:

| | macOS (NWProtocolTCP) | Android (Socket + Os.setsockoptInt) |
|---|---|---|
| Nagle | `noDelay = true` | `tcpNoDelay = true` |
| keepalive | idle 10 с, interval 5 с, count 36 (~3 мин) | KEEPIDLE(4)=10, KEEPINTVL(5)=5, KEEPCNT(6)=36 |
| предел ретрансмиссий | `connectionDropTime = 190` | TCP_USER_TIMEOUT(18) = 190 000 мс |
| ACK | `disableAckStretching = true` | TCP_QUICKACK(12) перед каждым чтением (как было) |
| приоритет Wi-Fi (WMM) | `serviceClass = .interactiveVideo` | `trafficClass = 0xA0` (CS5 → AC_VI) |
| сеть | — | сокеты привязаны к сети Wi-Fi (`Network.bindSocket`) |
| закрытие для переподключения | `forceCancel()` (RST) | `setSoLinger(true, 0)` + `close()` (RST) |
| обычное закрытие | CloseSession (0x1003, ≤ 0,5 с), затем `cancel()` | CloseSession, затем `close()` |

## Переподключение (контроллер)

- Транспорт закрылся с причиной «оборвалось / сброшено / камера не отвечает», а сеанс уже показывал кадры → режим
  «восстанавливаю связь»: кадр, свойства, таймер записи остаются; фаза `connecting`; попытки по тому же адресу сразу,
  затем через 0,5, 1, 2, 3, 5, 5… с; тайм-ауты попытки короче (TCP 2 с, Init 3 с).
- Не удалось за 60 с, или камера отказывает в TCP (PC Remote выключен) → обычное ожидание: экран «Подключите камеру»,
  поиск SSDP, паузы 2/4/8/10 с, как раньше.
- Init Fail: забывать сопряжение только при причине 1 (не сопряжена); 2 (занята) и 3 — повторить позже.
- После переподключения — обычное рукопожатие и успокоение 3 с; live view идёт сразу, кнопки — через 3 с.

## Качество превью (LiveViewQualityPolicy — чистая логика, с тестами)

Каждый кадр даёт отсчёт: байты, время запроса (от отправки GetObject до ответа), RTT — по пробам и коротким ответам
AccessDenied (минимум за 10 с), уровень — по ширине кадра (1024 — высокое, 640 — низкое).

- Пропускная способность `G = Σбайт / Σ(время − RTT)` за окно — только по быстрым кадрам (запрос ≤ 1,5 с): замирание
  связи — не узкий канал. Прогноз частоты на высоком `fpsH = min(25, 1 / (RTT + размерH / G))`, где размерH — средний
  размер кадра высокого (по умолчанию 72 КБ).
- **Вниз:** на высоком не меньше 5 с, окно 5 с, не меньше 8 быстрых кадров и `fpsH < 12` → низкое; либо 3 замирания
  дольше 1,5 с за 20 с. Одно замирание качество не снижает.
- **Вверх:** на низком, не раньше конца выдержки и не меньше 10 с на низком, окно 10 с, не меньше 30 кадров, ни одного
  замирания и `fpsH ≥ 18` → высокое.
- Выдержка после спуска вниз — 15 с; если после подъёма опять пришлось спуститься в течение 15 с — выдержка ×2 (до 5 мин);
  после 2 мин устойчивого высокого — снова 15 с.
- Во время провала связи решений нет (нет данных).
- В начале сеанса по Wi-Fi (после `ready`): если камера на низком, а настройка включена — сначала высокое, дальше по каналу.
  При выключенной настройке — всегда высокое.

## Экран

- Кадров нет 1,2–4 с: плашка «Слабый сигнал Wi-Fi» сверху, кадр не тускнеет.
- Провал связи или кадров нет ≥ 4 с: кадр приглушён, по центру «Связь с камерой прервалась · 0:07» и спиннер, после 10 с —
  совет (поднести камеру ближе к роутеру, на Mac — выключить AirDrop/Handoff, на планшете — Bluetooth).
- Переподключение: «Переподключаюсь к камере…».
- Снижено качество: в плашке состояния «640p», в подсказке о связи — почему.

## Платформенное

- **macOS:** `ProcessInfo.beginActivity([.userInitiated, .latencyCritical, .idleSystemSleepDisabled,
  .idleDisplaySleepDisabled])`, пока идёт сеанс с картинкой (App Nap душил превью до 6–12 к/с); объединение обновлений
  свойств по событиям 0xC203 (одно в работе и не больше одного в очереди).
- **Android:** `WifiLock` `WIFI_MODE_FULL_LOW_LATENCY` на время сеанса по Wi-Fi; привязка сокетов и SSDP к сети Wi-Fi;
  `NetworkCallback` (пропала сеть Wi-Fi — провал сразу; появилась — попытка сразу); в фоне (onStop) live view на паузе,
  через 60 с в фоне — обычное закрытие, в onStart — продолжение; честный (FIFO) замок транзакций вместо `@Synchronized`;
  объединение обновлений по 0xC203; ошибка разбора пакета — обрыв, а не вечный цикл; переиспользование Bitmap
  (`inBitmap`, пул из 3) и декодирование прямо из ответа со смещением.

## Проверка

- Модульные тесты: политика качества, решения слежения за связью (время подставляется), паузы переподключения, причины
  Init Fail.
- Стенд `scripts/badnet.py` (прокси для обоих соединений PTP/IP) + настоящая камера: хороший канал, «слабый», «плохой»,
  «ужасный», провалы 3/10/25 с, RST, потерянный FIN, падение полосы с последующим восстановлением, долгий прогон.
  Ограничение стенда: без root он не изображает потери на уровне TCP (ядро прокси подтверждает keepalive).
