# Протокол камеры

Как Sony Cam Viewer управляет камерой Sony по USB и по Wi-Fi: транспорт, установка связи, свойства и их значения, кнопки, съёмка, превью и подводные камни.

Поведение камеры описано по ZV-E10 с прошивкой 2.00 (Mac — macOS 27), если не сказано иное. В режиме PC Remote камера видна как USB-устройство `054c:0d97`, расширение Sony — версии `0x012C`: 93 свойства и 29 команд управления.

Официальный Sony Camera Remote SDK первую ZV-E10 не поддерживает. Справочником служили libgphoto2 (`camlibs/ptp2`: `ptp.h`, `ptp.c`, `ptp-pack.c`, `config.c`, лицензия LGPL) и Sony Camera Control PTP 3 Reference (описание свойств и команд для камер с 2020 года). Код программы написан заново, из libgphoto2 ничего не скопировано.

## Транспорт

Программа работает через системный ImageCaptureCore, без libusb, драйверов и sudo.

1. `ICDeviceBrowser` с маской `camera | local` находит камеры. Нужны устройства с `usbVendorID == 0x054C` (Sony).
2. `requestOpenSession` открывает сессию. Программа ждёт ответа не дольше 10 секунд.
3. Каждая команда идёт через `ICCameraDevice.requestSendPTPCommand(_:outData:completion:)`.

**Команда** — USB-контейнер PTP:

| Поле | Размер | Значение |
|---|---|---|
| длина | u32 | 12 + 4 × число параметров |
| тип | u16 | 1 — команда |
| код операции | u16 | например, `0x9209` |
| transaction id | u32 | 0, система подставляет свой |
| параметры | u32 × N | |

**Данные к камере (`outData`)** — только само значение в кодировке типа свойства, без заголовка контейнера. Заголовок ImageCaptureCore добавляет сам. Если передать полный контейнер, камера примет его байты за значение и применит: баланс белого, например, переключается на Preset 1.

**Ответ.** В колбэк приходят контейнер ответа (код ответа — u16 по смещению 6, параметры — с 12-го байта) и данные. Данные иногда приходят с 12-байтным заголовком контейнера данных, иногда без него. Программа снимает заголовок, только если длина в нём равна размеру данных, тип равен 2 и код совпадает с операцией.

**События** приходят в `cameraDevice(_:didReceivePTPEvent:)` в виде контейнера: длина u32, тип u16, код u16, transaction id u32, параметры.

Программа ждёт ответа на каждую команду до 8 секунд. Отключение камеры видно по `didRemove`: после него все команды сразу заканчиваются ошибкой «отключено».

`ICDevice.delegate` в ImageCaptureCore — `assign`, а не `weak`. Объект-делегат надо отвязать до того, как он освободится, иначе следующий колбэк придёт в освобождённую память.

## Установка связи

| Шаг | Команда | Зачем |
|---|---|---|
| 1 | GetDeviceInfo `0x1001` | модель, прошивка, список операций. Если среди операций нет `0x9201`, камера не в режиме PC Remote |
| 2 | `0x9201(1, 0, 0)` | начало рукопожатия Sony (SDIO Connect, фаза 1) |
| 3 | `0x9201(2, 0, 0)` | фаза 2 |
| 4 | `0x9202(0x12C, 1)` | версия протокола и списки кодов свойств и команд. Первые ответы бывают пустыми: повторять, пока не придут данные (программа — до 20 раз через 100 мс) |
| 5 | `0x9201(3, 0, 0)` | фаза 3, конец рукопожатия |
| 6 | `0x9205(0xD25A)`, значение 1 (INT8) | PriorityMode: управление переходит к компьютеру |
| 7 | `0x9209` | первое чтение всех свойств |
| 8 | пауза около 3 секунд, снова `0x9209` | после этого камера принимает настройки |

Без шага 6 камера отдаёт диафрагму как «только чтение» с пустым списком значений. После него диафрагма сразу изменяемая; список значений зависит от объектива (например, 19 значений, f/2.8–f/22).

Первые примерно 3 секунды после рукопожатия камера отвечает OK на запись настроек съёмки, но молча их игнорирует (например, баланс белого не меняется). libgphoto2 для ZV-E10 тоже ждёт 3 секунды. Превью работает и в эти секунды.

Ответ `0x9202`: u16 версия, затем массив кодов свойств (u32 число + u16 коды) и массив кодов команд управления того же вида.

С приоритетом у компьютера кнопки и колёса на самой камере продолжают работать. Изменения приходят событиями `0xC203`.

## Чтение свойств

GetAllExtDevicePropInfo `0x9209` возвращает все свойства сразу.

Заголовок: u32 количество, u32 резерв. Дальше описатели подряд:

| Поле | Размер | Значение |
|---|---|---|
| код | u16 | например, `0x5005` |
| тип | u16 | тип данных PTP, см. ниже |
| getSet | u8 | 1 — можно менять |
| enabled | u8 | 0 — недоступно, 1 — доступно, 2 — только показ |
| значение по умолчанию | по типу | |
| текущее значение | по типу | у строкового свойства в самом конце буфера может отсутствовать |
| formFlag | u8 | 0 — ничего, 1 — диапазон, 2 — список |
| диапазон | 3 значения по типу | min, max, step (при formFlag 1) |
| список | u16 N + N значений | при formFlag 2 |

У части свойств-списков сразу за первым списком идёт второй. Признак: следующий u16 меньше `0x200`. Если там код свойства (`0x5xxx`, `0xDxxx`), второго списка нет. Первый список у ZV-E10 — значения, которые можно поставить сейчас, второй — полный.

Типы данных PTP: `0x0001` int8, `0x0002` uint8, `0x0003` int16, `0x0004` uint16, `0x0005` int32, `0x0006` uint32, `0x0007` int64, `0x0008` uint64, `0xFFFF` строка. Строка PTP — u8 число символов, включая завершающий ноль, затем символы UTF-16LE.

Программа считает свойство изменяемым, если `getSet == 1` и `enabled == 1`. Список допустимых значений берёт из первого списка, а если его нет — строит из диапазона.

## Запись свойств

SetExtDevicePropValue `0x9205`, параметр — код свойства, в `outData` — значение в кодировке его типа.

- Камера применяет значение примерно за 0,6 секунды и присылает событие `0xC203`.
- Ответ OK ещё не значит, что значение принято. Программа подтверждает запись чтением: перечитывает `0x9209` каждые 150 мс, пока значение не совпадёт, но не дольше 2,5 секунды.
- Значение должно быть из списка допустимых (или попадать в диапазон с нужным шагом). Иначе программа его не отправляет.
- По каждому свойству одновременно идёт одна запись. Всё, что пользователь успел выбрать за это время, схлопывается в последнее значение.

## События

| Код | Смысл |
|---|---|
| `0xC203` | свойство изменилось — перечитать `0x9209` |
| `0xC207` | приходит, смысл неизвестен; программа не использует |

## Кнопки

Control Device `0x9207`: параметр — код кнопки, в `outData` — u16: 2 — нажать, 1 — отпустить.

| Кнопка | Код | Состояние |
|---|---|---|
| запись видео | `0xD2C8` | `0xD21D`: 1 — идёт запись |
| спуск наполовину (S1) | `0xD2C1` | `0xD213` (FocusFound): 2 или 3 — фокус найден |
| спуск полностью (S2) | `0xD2C2` | `0xD215` (ObjectInMemory): больше `0x8000` — снимок готов |

**Запись видео.** `0xD2C8` — Movie Rec Button (Hold) по справочнику Sony Camera Control PTP 3: команда работает как удержание кнопки — нажать (`2`) начинает запись, отпустить (`1`) останавливает.

- Программа начинает запись только нажатием, а свою запись останавливает только отпусканием, после чего ждёт смены `0xD21D`.
- Запись, начатую кнопкой на корпусе, программа останавливает нажатием и отпусканием.
- Если камера остановила запись сама, пока кнопка у программы нажата, перед следующим нажатием программа её отпускает.
- Отпускание, отправленное сразу за нажатием, камера иногда выполняет уже после старта, и запись кончается через ~0,5 с. Поэтому программа так не делает.
- Movie Rec Button (Toggle) `0xF001` у ZV-E10 нет.
- Камера может отклонить нажатие или отпускание (DeviceBusy `0x2019`) и всё же начать запись — или начать и тут же бросить. После отказа программа ждёт смены `0xD21D` до 2,5 с и сама нажатие не повторяет. Запись, кончившуюся в первые 3 с после запуска из программы, программа считает отказом камеры.
- Остановка у ZV-E10 занимает около 2 с от отпускания до смены `0xD21D`.

Сценарии для стенда — `scripts/e2e_record.py` с поддельной камерой `scripts/fake_camera.py --record …` (отпускание во время старта — `release-race`).

## Съёмка и скачивание снимка

1. S1: `0x9207(0xD2C1)` = 2.
2. Если фокус не ручной (`0x500A` ≠ 1), ждать FocusFound `0xD213` ∈ {2, 3} не дольше секунды.
3. S2: `0x9207(0xD2C2)` = 2, затем `0x9207(0xD2C2)` = 1.
4. S1: `0x9207(0xD2C1)` = 1.
5. Перечитывать свойства, пока ObjectInMemory `0xD215` не станет больше `0x8000`. Программа ждёт до 10 секунд.
6. GetObjectInfo `0x1008(0xFFFFC001)` — имя файла (например, `DSC02053.JPG`), размер, формат.
7. GetObject `0x1009(0xFFFFC001)` — сам файл.
8. При RAW+JPEG объектов два: после первого файла снова проверить `0xD215`, второй появляется следом.

Сколько файлов ждать, программа знает по формату снимка FileFormat `0xD253` (1 RAW, 2 RAW+JPEG, 3 JPEG): забрав их, она перечитывает свойства ещё раз и, если в памяти камеры пусто, сразу заканчивает. Без этого после каждого файла пришлось бы ждать следующего ещё до 2,5 секунды: JPEG по Wi-Fi освобождал бы спуск через 5,3 с вместо 2,5. Формат неизвестен — программа так и ждёт.

Если в памяти камеры уже что-то лежит до снимка (прошлый снимок не забрали: длинная выдержка не уложилась в 10 секунд, оборвалась загрузка по Wi-Fi, формат сменили перед снимком), значение `0xD215` до полунажатия больше `0x8000` на число таких объектов. Программа ждёт и их и забирает вместе с новым снимком. Без этого ранний выход забирал бы старый файл, а новый оставался бы в камере — и каждый следующий снимок сохранялся бы на один позже.

Долю загрузки по Wi-Fi видно по самому потоку: Start Data `0x9` несёт полную длину данных, а принятые байты транспорт считает до ответа на операцию. По USB на Mac (ImageCaptureCore) доли не видно; на Android USB длина берётся из заголовка первого контейнера данных.

Если шаг 2 или 3 сорвался, обе кнопки нужно отпустить. Иначе спуск остаётся полунажатым.

Куда камера сохраняет снимок, задаёт `0xD222` (Still Image Save Destination):

| Значение | Куда |
|---|---|
| `0x01` | только компьютер: файл ждёт в памяти камеры, на карту не пишется |
| `0x10` | только карта: скачивать нечего |
| `0x11` | компьютер и карта |

## Фокус и зум с экрана

Команды Control Device `0x9207` со значением своего типа (не кнопки «нажать / отпустить»). Какие из них камера знает, видно по второму списку ответа GetExtDeviceInfo `0x9202`: у ZV-E10 там все пять.

| Команда | Код | Значение | Когда работает |
|---|---|---|---|
| точка AF | `0xD2DC` | UINT32: x в старших двух байтах, y в младших; сетка 640×480 на весь кадр превью | двигает рамку в зонах «Точка» (`0x101`–`0x104`) и «Зона» (`0x2`), они же со слежением (`0x202`, `0x204`–`0x207`); в «Широкой» ничего не делает |
| касание экрана камеры | `0xD2E4` | UINT32, как у точки AF | при Remote Touch Enable `0xD284` = 1; что делает — как касание экрана камеры: Touch Focus или Touch Tracking (Function of Touch Operation `0xD283`: 3 — фокус, 4 — слежение) |
| снять касание | `0xD2E5` | UINT16, кнопка: 2, затем 1 | при `0xD285` = 1 — пока идёт слежение от касания |
| зум | `0xD2DD` | INT8: 1 — к теле, −1 — к широкому, 0 — стоп | при Zoom Operation Enable `0xD25B` = 1; зум едет, пока не придёт 0 |
| ближе / дальше | `0xD2D1` | INT16: −7…−1 — ближе, 1…7 — дальше | при Near/Far Enable `0xD235` = 1: у ZV-E10 — в ручном фокусе |

Свойства для показа:

| Свойство | Код | Кодировка |
|---|---|---|
| положение фокуса | `0xD24C` | UINT8, 0…100 |
| масштаб зума | `0xD25C` | UINT32, ×1000: 1000 — ×1,0; у ZV-E10 с Clear Image Zoom — 1000…1500 шагом 100 |
| шкала зума | `0xD25D` | UINT32: биты 31–24 — сколько отрезков, 23–16 — в каком (с 0), 15–0 — где в нём (0…100) |
| Clear Image / цифровой зум | `0xD25F` | 1 — только оптический, 3 — Clear Image Zoom, 4 — цифровой |

Как программа ими пользуется:

- **Фокус касанием.** В зонах «Точка» и «Зона» — точка AF, иначе — касание экрана камеры, но только если касание в камере ставит фокус или слежение (`0xD283` = 3, 4 или 8–11): касание-спуск (2, 6, 7) сделало бы снимок. В ручном фокусе — никак. Точка кадра (доли) переводится в сетку 640×480: x × 639, y × 479.
- **Команды объектива идут по одной и по порядку**: «стоп» зума не обгонит «пуск». Связь оборвалась или камеру сменили, пока держали «T» или «W», — уходящему сеансу шлётся «стоп», кнопка отпускается, очередь шагов фокуса сбрасывается.
- **Зум.** Пока держат «T» или «W», — 1 или −1, отпустили (и при любом обрыве жеста, уходе экрана) — 0. Повтор того же направления не шлётся.
- **Шкала фокуса.** Шаги 1, 3 и 7; перетаскивание по шкале раскладывается на команды не больше 7 и шлётся по одной, следующая — после ответа на прошлую.

Где камера фокусирует, видно по рамкам в каждом кадре превью (см. ниже).

Кодировки в этом разделе — по справочнику Sony и libgphoto2. У ZV-E10 все пять команд есть в её списке, а свойства `0xD235`, `0xD24C`, `0xD25B`–`0xD25F` и `0xD283`–`0xD285` она отдаёт (в AF-C: Near/Far закрыт, зум открыт, касание экрана открыто, функция касания — слежение). Что показала ZV-E10 по Wi-Fi:

- **Точка AF** ставит рамку ровно туда, куда просили: (0,3; 0,5) → (0,3; 0,5), (0,75; 0,25) → (0,748; 0,25), (0,5; 0,8) → (0,5; 0,797). X и Y в рамках — её центр; рамка «Точки L» — 0,153 × 0,206 кадра. В ручном фокусе рамка остаётся в кадре (состояние — не «фокус найден»).
- **Касание экрана** в «Широкой» с функцией «слежение» начинает слежение; рамка слежения садится на предмет рядом с точкой касания, а не ровно в неё. `0xD2E5` слежение снимает.
- **Near/Far**: отрицательное — ближе. −7 дважды: `0xD24C` 94 → 73 → 47; +7 дважды: 47 → 75 → 100. Шаги ±3 сразу после этого, у дальнего края, положение не сдвинули.
- **Зум с PZ 16-50**: шкала `0xD25D` — два отрезка, оптика (отрезок 0) и Clear Image Zoom (отрезок 1). Оптика от 16 до 50 мм проходит примерно за 2,3 с непрерывного «T»; всё это время масштаб `0xD25C` — ×1,0, зона фокуса и касание экрана не меняются, а диафрагма меняется вместе с фокусным расстоянием (f/3.5 → f/4 → f/5.6), и камера сообщает её как обычно. За длинным концом зум уходит во второй отрезок — Clear Image Zoom, как ниже. «W» до упора возвращает всё как было.
- **Зум** с объективом без электропривода сразу ведёт Clear Image Zoom (шкала — один отрезок): масштаб `0xD25C` доходит до ×1,1, положение на шкале `0xD25D` — 13–20. Пока масштаб больше ×1,0, камера ставит зону фокуса «Центр» (`0x3`) и закрывает касание экрана (`0xD284` = 0): точку AF не подвинуть, касания нет. На ×1,0 зона и касание возвращаются. Программа тогда так и пишет: «Пока зум больше ×1,0, камера не даёт ставить фокус касанием».

Поддельная камера `scripts/fake_camera.py` ведёт себя так же, только зум у неё — как у PZ 16-50: «наезжает» картинкой и зону фокуса не трогает. Сквозные проверки — `scripts/e2e_lens.py`.

## Превью (live view)

GetObject `0x1009(0xFFFFC002)`. В начале ответа — заголовок Sony: u32 смещение до JPEG (у ZV-E10 — 1524) и u32 размер JPEG, затем u32 смещение и u32 размер блока рамок фокуса FocalFrameInfo (у ZV-E10 — 1012 и 120 байт). С первого смещения идёт сам JPEG. На всякий случай программа умеет найти начало JPEG (`FF D8 FF`) и без заголовка.

**Рамки фокуса** (FocalFrameInfo, версия 1.01 у ZV-E10): u16 версия ×100 и резерв до 8 байт, 40 байт резерва, u16 число резервных записей и резерв до 8 байт, сами записи по 24 байта; затем три раздела — рамки AF, лица (с версии 1.01), слежение (с 1.01). У каждого раздела u32 знаменатели X и Y (у ZV-E10 — 640×1024 и 480×1024), u16 число рамок и резерв до 16 байт, потом рамки по 24 байта: u16 тип, u16 состояние (2 — фокус найден), u8 приоритет и резерв, u32 X, u32 Y (центр рамки), u32 высота, u32 ширина — числители к знаменателям раздела. Программа рисует эти рамки поверх кадра, пока включён фокус касанием.

- Около 20–24 кадров в секунду.
- 1024×576 в видеорежиме. В фоторежиме размер зависит от пропорций снимка: при 1:1 — 1024×1024.
- Около половины запросов возвращают AccessDenied `0x200F`: кадр ещё не готов. Нужно повторить через 20 мс.
- Пока превью поднимается, приходит InvalidObjectHandle `0x2009`: повторить через 50 мс.
- Во время смены режима бывает DeviceBusy `0x2019`: тоже повторить.
- Свойство LiveViewImageQuality `0xD26A` по USB на кадр не влияет: 1 и 2 дают одинаковые кадры. По Wi-Fi влияет, см. [Wi-Fi (PTP/IP)](#wi-fi-ptpip).

| Свойство | Код | Кодировка |

| профиль изображения | `0xD23F` | 0 выкл, 1–10 — PP1–PP10 |

**S&Q.** Режим S&Q включается тем же `0x500E`: S&Q P/A/S/M — `0x98059`–`0x9805C` (видео — `0x78050`–`0x78053`, физическая кнопка MODE переключает их же). Параметры записи ролика в S&Q — тот же `0xD242`. Частоту съёмки S&Q (1–100 к/с) ZV-E10 не отдаёт ни одним из 95 свойств и менять не даёт: при её смене на камере меняются только список допустимых выдержек `0xD20D` (самая длинная — 1/100, 1/50, 1/25, 1/13, 1/6, 1/3, 0,5″, 1″ при 100, 50, 25, 15, 8, 4, 2, 1 к/с), остаток времени на карте `0xD24A`, доступность цифрового зума `0xD25B`–`0xD25F` (при 100 к/с его нет) и `0xD283` (3 при 100 к/с, иначе 4). Программа узнаёт частоту по самой длинной выдержке. Из 29 команд управления камеры кнопки-стрелки есть (`0xD2CD`–`0xD2D0`), а MENU и OK нет, так что пройти меню за пользователя нельзя; `0xD2E6` — по справочнику Sony спуск S1 и S2 одной командой, назначение трёх (`0xD2DA`, `0xD2DB`, `0xD2E8`) неизвестно, и проверять их вслепую не стоит — среди соседних есть форматирование карты (`0xD2CA`).

Температуру пресетов и автобаланса камера не сообщает. В любом режиме `0xD20F` возвращает сохранённую ручную температуру (у нас — 7400 K и в AWB, и в «Лампе»), а сравнение всех 95 свойств в AWB, «Дневном», «Лампе» и «Цвет. темп.» показало, что меняется только сам `0x5005`. Поэтому программа показывает температуру только в режиме `0x8012`, для пресетов — примерную, для AWB — «авто». Ползунок вне `0x8012` сначала переключает режим, ждёт, пока `0xD20F` станет записываемым (обычно ~0,8 с), и только потом пишет температуру.

Направление сдвигов видно по цвету кадра: при A–B = 220 отношение R/B в кадре выросло до 1,69, при 164 упало до 0,61. Камера хранит сдвиги отдельно для каждого режима баланса белого: чтобы вернуть сдвиг, сначала переключитесь в тот режим, где его меняли.

## Другие камеры Sony

Всё выше описано по ZV-E10. Про другие камеры известно из исходников libgphoto2:

- **Версия протокола.** В запросе `0x9202` программа просит версию 3.00 (`0x12C`). Камера, которая её не поддерживает, отвечает своей максимальной версией — это первое u16 ответа. Программа версию не проверяет.
- **Версия 3.00** — по документации Sony, «для моделей 2020 года и новее». В ней выдержка, ISO и диафрагма пишутся напрямую, как описано выше.
- **Версия 2** — у камер постарше. libgphoto2 меняет у них ISO, выдержку и экспокоррекцию шагами («old method, using stepping»), а не прямой записью значения. Программа так не умеет.
- **Пустой ответ на `0x9202`.** Некоторые камеры отвечают без данных, libgphoto2 считает их версией 2. Программа в этом случае ждёт данных, после 20 попыток считает подключение неудачным и повторяет его.
- **PriorityMode.** Если камера отклонит запись `0xD25A`, программа сочтёт подключение неудачным. Есть ли это свойство у старых камер, неизвестно.
- **Пауза перед съёмкой.** libgphoto2 после подключения ждёт около 3 секунд перед первым снимком не только у ZV-E10, но и у ZV-1, RX100 VII, a7 III, a7 IV, a7R IV, a7S III, a9 II, a1 и a7C.
- **USB-идентификатор** у каждой модели свой: у ZV-E10 в режиме PC Remote — `054c:0d97`. Программа отбирает камеры только по производителю (`0x054C`), так что модель ей не важна.

### Таблицы из справочника Sony

В репозитории лежат таблицы названий свойств и подписей значений из справочника Sony «Camera Control PTP 3 Reference» (издание August 2025): они нужны камерам, которые сами подписей не отдают. Сам PDF в репозиторий не кладётся — это документ Sony. Скачать его можно отсюда (на странице — «Download raw file»): <https://github.com/jakkuh/sony-alpha-python/blob/main/docs/Camera%20Control%20PTP%203%20Reference.pdf>.

Таблицы строятся из текста PDF (`pdftotext` входит в poppler: `brew install poppler`):

```
pdftotext -layout "Camera Control PTP 3 Reference.pdf" ptp3.txt
scripts/sony_reference.py ptp3.txt
```

Скрипт пишет один и тот же JSON в два места: `Sources/ZVCore/Sony/SonyReferenceData.swift` (JSON в строке Swift, для Mac) и `android/app/src/main/resources/sony_reference.json` (ресурс Android). Оба файла лежат в репозитории. Править таблицы можно скриптом или прямо в JSON, но сразу в обоих местах: тест `androidCopyMatches` сверяет, что они одинаковы. Читают их `SonyReferenceTables` в ZVCore и `SonyReferenceTables` в `local.zve10viewer.sony`.

В JSON — все 737 свойств справочника: код, название и, если справочник перечисляет значения, список «значение → подпись» (таких свойств 523, значений в них 2929). Подписи — как в справочнике, по-английски. Коды и значения — шестнадцатеричные, как там же: `"0xD0FA"`, `"0x0B"`. Значение `0xFFFFFFFFFFFFFFFF` (UINT64) читается как −1, так же, как значение из камеры.

Как скрипт читает текст:

- **Название** — строка над ближайшим выше «Summary».
- **Значения** — строки «код  описание» первой таблицы «Value  Description» раздела, до «Note» или следующего «Summary». Номер страницы, колонтитул и повторённый заголовок, которыми страницы рвут таблицу, пропускаются; пробелы подряд в описании схлопываются в один.
- **Значение без описания в своей строке** (0xD221): код стоит посередине высокой ячейки, описание — строка над ним и строка под ним.
- **Чего в списках нет.** Границы диапазонов (min, max, step; диапазоны вроде `0x00 ～ 0xFF`), «Any», «Other than above values» и пояснения в ячейках; если других значений у свойства нет, остаётся только название. Таблицы внутри «Note» (0xE068, 0xE06C, 0xE082) описывают разряды составного значения, а не само свойство — они тоже не берутся.
- **Разделы команд управления** (`ControlCode`) в таблицы не входят: только свойства (`PropertyCode`).

## USB напрямую (Android)

На Mac контейнеры PTP, номера транзакций и чтение ответов берёт на себя ImageCaptureCore. На Android программа говорит с камерой через USB host сама (`UsbPtpTransport`).

- **Интерфейс** — класс 6 (Still Image): bulk OUT для команд и данных, bulk IN для данных и ответов, interrupt IN для событий.
- **Обмен:** контейнер команды → при записи контейнер данных (заголовок 12 байт + значение) → чтение контейнера данных (если он есть) и контейнера ответа. Длина в заголовке первого пакета говорит, сколько дочитать. Данные, кратные 512 байтам, камера завершает пакетом нулевой длины — его надо пропустить.
- **Номера транзакций:** вне сессии — 0, после OpenSession — 1, 2, 3… Программа открывает сессию первой командой (до GetDeviceInfo), а контейнеры с чужим номером транзакции или чужим кодом в данных отбрасывает: так остатки оборванного обмена не принимаются за новый ответ.
- **Читать кусками по 16 КБ.** Чтение крупным буфером (256 КБ) на части устройств не проходит. Тогда ответ остаётся в камере, и она перестаёт принимать команды: каждая следующая запись падает.
- **Сброс при подключении:** классовый запрос Device Reset (`0x21`, `0x66`), снятие «залипания» с обоих bulk-каналов (CLEAR_FEATURE ENDPOINT_HALT), опрос Get Device Status (`0xA1`, `0x67`) до `0x2001` и вычитывание остатков, пока два раза подряд ничего не придёт.
- **Первая команда после перезапуска программы** иногда остаётся без ответа: OpenSession ждёт 1,5 с и повторяется до четырёх раз: с обычным тайм-аутом 8 с картинка появлялась бы только через 11 с.
- **События — асинхронным запросом** (`UsbRequest` + `requestWait`) без тайм-аута. Синхронное чтение interrupt-канала с тайм-аутом 500 мс на Redmi Pad Pro каждые ~1,5 с задерживает ответ на запрос кадра на 150–225 мс, и видео заметно дёргается.
- **Опрос превью:** после AccessDenied ждать 5 мс, а не 20: кадр у камеры готов раз в 40 мс, и длинная пауза сбивает ровность. Итог на планшете — 25 кадров/с, 90% интервалов не длиннее 47–49 мс.

### Яркость превью

Уровень белого в JPEG превью зависит от режима. В видео (и S&Q) пересвеченное место ложится столбиком ровно на яркость 234 из 255 (окно при +3 ступенях — 19 % кадра на 234, выше — только единичные точки до 239 от сжатия JPEG), в фото — на 255. Чёрное в обоих режимах — 0–1. Гистограмма в программах поэтому идёт от 0 до белого текущего режима; если в видео больше 0,1 % точек ярче 240 (профиль с полной шкалой), белым считается 255.

## Wi-Fi (PTP/IP)

По Wi-Fi камера говорит тем же PTP, только поверх TCP — по стандарту CIPA DC-005 (PTP/IP). Команды Sony, свойства и события те же, что по USB; отличаются транспорт, поиск камеры и сопряжение. Ниже описан режим Wi-Fi Access Point, когда камера подключена к роутеру; Wi-Fi Direct — в конце раздела.

**Настройка камеры:** MENU → Network → Wi-Fi Settings → Access Point Set. (ZV-E10 — только 2,4 ГГц), PC Remote Cnct Method: Wi-Fi Access Point.

**Поиск — SSDP.** Программа шлёт M-SEARCH на `239.255.255.250:1900` с `ST: urn:schemas-sony-com:service:DigitalImaging:1`. Камера отвечает с `SERVER: UPnP/1.0 SonyImagingDevice/1.0` и `LOCATION: http://<адрес>:64321/dd.xml`; в описании `DigitalImagingDesc.xml` — `X_PTP_PairingNecessity: Necessary`. Отвечает камера не сразу, через 1,2–2,7 с, а многоадресные пакеты по Wi-Fi теряются, поэтому запрос повторяется каждые 0,7 с в окне 4 с. В USN — MAC-адрес камеры.

**Два TCP-соединения на порт 15740:** команд с данными и событий. Пакет: u32 длина (вместе с заголовком), u32 тип, содержимое.

| Тип | Пакет | Содержимое |
|---|---|---|
| 1 | Init Command Request | GUID программы (16 байт), имя UTF-16LE с нулём («ZV-E10 Viewer», с планшета — «ZV-E10 Viewer Android»), версия u32 `0x00010000` |
| 2 | Init Command Ack | номер соединения u32, GUID камеры, имя камеры, версия |
| 3 | Init Event Request | номер соединения |
| 4 | Init Event Ack | — |
| 5 | Init Fail | причина u32: 1 — программа не сопряжена, 2 — камера занята, 3 — без причины |
| 6 | Operation Request | фаза данных u32 (1 — без данных к камере, 2 — с ними), код операции u16, transaction id u32, параметры |
| 7 | Operation Response | код ответа u16, transaction id, параметры |
| 8 | Event | код u16, transaction id, параметры |
| 9 | Start Data | transaction id, полная длина u64 |
| 10 | Data | transaction id, кусок данных |
| 11 | Cancel | transaction id: прервать идущую передачу (камера отвечает `0x201F`); программы его не шлют |
| 12 | End Data | transaction id, последний кусок |
| 13 / 14 | Probe Request / Response | проверка связи по соединению событий: на запрос надо ответить сразу. Камера отвечает на пробу программы за 5–50 мс |

**Подключение:** соединение команд → Init Command Request → Ack с номером соединения → соединение событий → Init Event Request → Ack → OpenSession, дальше та же последовательность Sony, что по USB (`0x9201`, `0x9202`, PriorityMode, пауза 3 с). По Wi-Fi камера отдаёт 95 свойств против 93 по USB.

**Сопряжение.** Камера принимает только сопряжённые программы: незнакомому GUID она отвечает Init Fail с причиной 1. Когда на камере открыт пункт PC Remote Function → Pairing, тот же Init Command Request камера показывает на экране и после подтверждения запоминает GUID. Программа создаёт GUID один раз и хранит его; на Mac его делят программа и `zv-probe`. Камера помнит несколько устройств — Mac и планшет сопряжены одновременно, — но держит одно подключение за раз.

Имя в Init камера показывает при сопряжении и под ним помнит сопряжение. Поэтому программы представляются именами из таблицы, а не названием Sony Cam Viewer: с другим именем камера могла бы сопряжение не узнать.

**Данные.** Запись значения: Operation Request с фазой 2, Start Data с длиной, End Data со значением. Чтение: Start Data → Data → End Data → Operation Response. Кадр превью приходит одним куском, большой файл — пакетами Data по 2 МБ. Скорость скачивания снимка — около 5 МБ/с на планшет.

**Качество превью по Wi-Fi — `0xD26A` (LiveViewImageQuality, UINT8).** По Wi-Fi оно меняет кадр (по USB разницы не видно): 2 — высокое, 1024×576, ~72–75 КБ на кадр; 1 — низкое, 640×360, ~34 КБ. Размер кадра почти не зависит от сюжета. Высокое при 25 кадрах/с — ~1,8 МБ/с (~14 Мбит/с), это близко к потолку 2,4 ГГц самой камеры: на слабом сигнале оно не помещается, и превью дёргается. Обе программы по Wi-Fi держат высокое, пока канал его тянет, и переходят на низкое, когда не тянет (см. [Устройство кода](architecture.md#связь-по-wi-fi-без-обрывов)). Запись — через `0x9205` без ожидания подтверждения: переход видно по ширине кадров.

**Подводные камни Wi-Fi:**

- **Первая команда сразу после сопряжения** может остаться без ответа. Помогает короткий тайм-аут OpenSession (1,5 с) с повтором; через секунду камера отвечает за 8–30 мс.
- **Оборванное подключение камера держит ~2,5 минуты.** Если до неё не дошло закрытие соединения (пропала сеть, macOS как раз переспрашивала доступ к локальной сети), новые подключения она отбрасывает, пока не выйдет срок. Нормальное закрытие освобождает её сразу. Через прокси `scripts/badnet.py` видно: пока старое соединение живо на уровне TCP, а программы за ним нет, новое подключение камера ~10 с не принимает (рвёт после Init или молчит на OpenSession), а потом сама отпускает старое — видимо, проверяет его пробой. RST по старому соединению освобождает камеру сразу: новый полный сеанс — через ~1,5 с. Поэтому программы не закрывают соединение, пока связи нет (закрытие туда не дойдёт), а когда связь вернулась и TCP молчит — сбрасывают его RST и подключаются заново.
- **Долгая тишина может выключить PC Remote.** После 25 с без единой команды и подключения (прокси держал соединение живым, но ничего не пропускал) ZV-E10 ещё ~17 с отвечала через раз, а потом сама переключила PC Remote Cnct Method на USB и пропала из сети: не отвечала ни на ping, ни на SSDP. Вернуть её в сеть можно, только снова выбрав на камере Wi-Fi Access Point. Похоже на сторож неактивности ~20–25 с; наблюдалось один раз, с какой длительности тишины это повторяется, неизвестно. С ~2,5 минутами из предыдущего пункта это не сходится — там камера, вероятно, застревает на неподтверждённой передаче.
- **Голый Init без продолжения.** Если после Init Command Ack сразу закрыть соединение, не открыв канал событий, камера какое-то время рвёт следующие подключения сразу после Init. Проверять камеру так нельзя.
- **Ping.** Камера отвечает на ICMP ping (3–13 мс). Это проверка, что сеть вернулась: TCP после долгого провала молчит ещё долго — повторы отправки идут с растущими паузами.
- **Отложенное подтверждение TCP.** Короткий ответ «кадр не готов» (AccessDenied) камера не отправляет, пока ей не подтвердили предыдущий сегмент, а Android откладывает подтверждение примерно на 40 мс. Каждый такой ответ шёл ~60 мс вместо ~25, и превью было 16–19 кадров/с вместо 25. На Android программа ставит `TCP_QUICKACK` перед каждым чтением сокета команд (Linux сбрасывает его сам).
- **Запрос кадра и декодирование — параллельно.** Запрос кадра по Wi-Fi идёт 25–35 мс. Если ждать, пока предыдущий кадр декодируется, выходит ~21–22 кадра/с, а параллельно — 25, сколько камера и отдаёт.
- **Связь «ждёт» на macOS.** Сразу после того как пользователь разрешил доступ к локальной сети, macOS на ~1,5 с помечает живые соединения как «Local network prohibited» (`NWConnection` в состоянии `waiting`). Это не обрыв: соединение возвращается само.
- **Wi-Fi Direct.** Камера сама раздаёт сеть `DIRECT-…` (WPA2, пароль на экране камеры), берёт себе адрес `192.168.122.1` и раздаёт клиентам адреса `192.168.0.x/16`. SSDP, приветствие и сеанс — те же. Сопряжение, сделанное в режиме роутера, действует и здесь. Превью — 23–25 кадров/с, RAW+JPEG — около 20 с от нажатия до файла, медленнее, чем через роутер. По адресу `192.168.122.1` программа узнаёт этот режим и пишет в строке состояния «Wi-Fi Direct».
- **Android и сеть без интернета.** К сети камеры планшет подключается из настроек Android (`cmd wifi connect-network` для adb на обычной прошивке закрыт). Android помечает её «нет доступа к интернету» и может вернуться на сеть с интернетом, если не подтвердить, что остаёмся.

## Подводные камни

- **`outData` — только значение.** Полный контейнер камера примет как мусор и применит его.
- **Первые 3 секунды камера пропускает запись настроек.** Ответ при этом OK, поэтому ошибку не заметить без проверки чтением.
- **Без PriorityMode часть свойств только для чтения**, в том числе диафрагма.
- **Подтверждать запись чтением.** OK от камеры значит «получила», а не «применила».
- **Сдвиги баланса белого — для каждого режима свои.**
- **Половина запросов превью — AccessDenied.** Это нормально, нужен быстрый повтор. По Wi-Fi каждый повтор стоит целого обмена по сети — см. [Wi-Fi (PTP/IP)](#wi-fi-ptpip).
- **`0xD20F` — не текущая температура**, а сохранённая ручная; температуру пресетов и автобаланса камера не сообщает.
- **Не держать спуск нажатым.** Если съёмка сорвалась посередине, отпустите S2 и S1.
- **Делегат ImageCaptureCore — `assign`.** Отвязывайте его перед освобождением объекта.
- **Опыты на камере пользователя.** Перед любой экспериментальной записью прочитайте текущее значение и потом верните ровно его. Пробовать запись лучше на безобидном свойстве, например LiveViewImageQuality `0xD26A`.

Для опытов есть утилита `zv-probe` (см. [Устройство кода](architecture.md#утилита-zv-probe)).
